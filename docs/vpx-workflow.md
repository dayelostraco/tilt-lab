# VPX source-control workflow

A `.vpx` file is an OLE compound document with the geometry in binary BIFF
records and the VBScript buried inside `GameStg/GameData`. Committing one
means committing a 17 MB opaque blob per change, which makes review
impossible. This project does not do that.

## The model

```
scripts/*.vbs  ──concat──▶  table/src/script.vbs  ──┐
                                                    ├─ vpxtool assemble ─▶  table/dist/Pinball Training Lab.vpx
table/src/gameitems/*.json ─────────────────────────┘
table/src/{gamedata,materials,collections,images,sounds}...
```

- **`table/src/` is the source of truth.** It is the fully extracted table:
  JSON per game item, `.obj` meshes, loose image and sound files, and the
  table-level settings in `gamedata.json`. All of it diffs as text or as
  individually replaceable media.
- **`table/dist/*.vpx` is a build artifact** and is gitignored. Never edit it
  expecting the change to survive.
- **`scripts/*.vbs` is the script source of truth.** `table/src/script.vbs` is
  generated by the build and carries a DO NOT EDIT banner.

`vpxtool` extract/assemble was verified lossless for this project's base
table: extracting, assembling and re-extracting produces a byte-identical
directory tree. The `.vpx` itself is not byte-identical between builds because
the OLE container's internal layout is not stable, which is why the artifact
is not tracked.

## Commands

```bash
tools/build.sh          # scripts/ + table/src/  ->  table/dist/*.vpx
tools/check.py          # static checks on the assembled script
tools/import.sh [vpx]   # pull editor changes back into table/src/
tools/vpxtool.sh ...    # run vpxtool directly (installs it on first use)
```

`tools/vpxtool.sh` downloads the pinned `vpxtool` release into `~/.local/bin`
on first use, so a fresh checkout builds with no manual setup beyond `curl`
and `python3`.

## Editing geometry

Two ways, both fine:

1. **Edit the JSON.** `table/src/gameitems/Flipper.LeftFlipper.json` is plain
   readable JSON with named fields (`center`, `strength`, `elasticity`, ...).
   For physics tuning this is faster and reviews far better than the editor.
2. **Edit in the VPX editor on Windows**, then run `tools/import.sh` against
   the edited file. Geometry changes land in `table/src/` as a JSON diff.

Editor round-trips have one trap: the script inside the `.vpx` is the
*generated* one. If you edit the script in the VPX editor, `tools/import.sh`
prints a warning and a diff, because the next `tools/build.sh` will overwrite
it from `scripts/`. Port such edits into the right module first.

## The `.vbs` sidecar trap

`vpxtool extractvbs` writes a `Table Name.vbs` next to the `.vpx`. When that
sidecar exists, **Visual Pinball loads it instead of the embedded script**.
That is useful for live script iteration on Windows, and it is an excellent
way to spend an hour wondering why a build had no effect. `.gitignore` blocks
committing one; delete the sidecar when you are done iterating.

## Base table is ahead of the shipped runtime

The first Windows run surfaced a stream of these in the VPX log:

```
ERROR [IEditable::LoadSharedEditableField] Unhandled token: BGLS
INFO  [BiffReader::AsObject] While reading tag BGLS 4 were not read and therefore skipped
```

`BGLS` is `m_desktopBackdrop`, a field written by every part. `blankTable.vpx`
comes from vpinball **master**, which writes it; the installed VPX 10.8.1.5436
(`af26b2d93`) predates it and does not read it.

It degrades gracefully: the 4-byte record is skipped and the field keeps its
default. Nothing breaks. But it logs an ERROR per part, which is noise that
will hide a real error later, so check the *token name* before believing a
`LoadSharedEditableField` error is ours.

This also means the base table is slightly ahead of the runtime it has to run
on. Worth remembering before blaming a future oddity on our own edits.

> Chased and cleared: `vpxtool` is **not** dropping this field. A raw scan of
> every OLE stream shows 23 live `BGLS` records before and after a round-trip.
> A naive byte count of the whole file reports 25 against 23, because the
> original carries two stale copies in unallocated sectors left by an earlier
> save.

## Reproducibility

`reference/base-table.sha256` pins the exact base table the repository was
seeded from, so the provenance of `table/src/` stays checkable even though the
original 17 MB `.vpx` is not committed.
